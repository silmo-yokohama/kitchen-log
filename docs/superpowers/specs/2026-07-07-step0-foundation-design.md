# Step0設計: リポジトリ基盤・スキーマ・AI運用ルール

> 作成日: 2026-07-07
> 関連Issue: https://github.com/silmo-yokohama/knowledge-hub/issues/5
> 関連ドキュメント: `knowledge-hub` リポジトリ `02.Ideas/2026-07-07_レシピ管理AIアレンジアプリ/`（overview.md, discussion.md, references.md）

## 背景・目的

料理レシピを構造化データとして蓄積し、Claude Codeで好み・過去レシピ・公的栄養データを参照しながらAIアレンジ・栄養評価した上で、スマホで見やすく・調理しやすく管理するアプリを作る。既存アプリ「CookGo」の「材料と手順が同期しない」「お気に入り・検索が弱い」という不満の解消が動機。

開発ロードマップは以下の4段階（Issue #5 より）。本ドキュメントは **Step0（リポジトリ構成・スキーマ・好みプロファイルの型を確定する）のみ** を対象とする。

- **Step0**（本ドキュメントの範囲）: リポジトリ構成・スキーマ・好みプロファイルの型を確定する
- Step1: 4つの入口（CookGo/URL/テキスト/ゼロベース）からレシピを変換・保存できる
- Step2: Astro製PWAビューア（一覧・詳細・人前スケーリング・検索・タグ絞り込み）
- Step3: 調理モード（手順を1ステップずつ大きく表示）

> 補記（2026-07-13）: Step2は「検索」ではなく選択式絞り込み（カテゴリー・素材・タグ）として実装済み（2026-07-12 Step2設計参照）。調理モード（Step3）は作らないことに決定（先送りではなく計画自体を廃止）。

v2以降（お気に入り・週間予定表・買い物リストのSupabase連携）は本ドキュメントのスコープ外。ただし将来の拡張を見越した技術選定・データ境界のルールはここで明文化する。

## 技術スタック（確定）

壁打ち段階の企画書に記載された技術スタックは、実際にはユーザーと詳細を詰めたものではなくAIが提案しただけだったため、非機能要件を洗い出した上でこの設計セッションで再検討し直した。

| 項目 | 決定 | 理由 |
|------|------|------|
| フロントエンド | Astro + Islands | v1の使用感の大半（レシピを探す・読む・調理モードで見る）は本質的に静的コンテンツであり、Astroは非対話ページでJSを一切出力しない（Islands Architecture）。パフォーマンスNFRに対し、Next.js/Nuxt等のSSGよりも有利。ISR（Incremental Static Regeneration）はコンテンツ変更が常にgit commit経由であるため不要（ISRが解決する「コード非依存のコンテンツ更新」という問題がそもそも発生しない） |
| レシピデータ形式 | JSON（gitリポジトリ） | レシピはClaude Code（AI）が生成・書き込みする前提であり、人間が生ファイルを手打ち編集する運用ではない。YAMLは曖昧な型変換（Norway Problem、`1:30`のような文字列が60進数と解釈される等）のリスクがあり、AI大量生成データには不向き。JSONはAstro Content Collectionsで同様にZodスキーマ検証が可能で、この点はYAMLと差がない |
| 好みプロファイル形式 | Markdown（`profile.md`） | プレーンな文章（蒸留された記憶）であり、数値・時刻のような型変換リスクがない。構造化データではないためJSONにする必要がない |
| ホスティング | Cloudflare Pages | セキュリティNFR（後述）に対応するため、GitHub Pagesから変更 |
| アクセス制御 | Cloudflare Access | 「二人以外に見せたくない」というセキュリティNFRに対応。無料枠が恒久的に50ユーザーまで対応（2026年時点で確認済み）。アプリ側のコード変更なしにインフラ層でアクセス制御でき、保守性NFRにも合致 |
| v2の対話的機能 | Supabase | お気に入り・週間予定表・買い物リスト等、アプリから直接読み書きする「日常操作」データの保存先（v2以降で実装） |

### 非機能要件（確認済み）

- **パフォーマンス**: 具体的な数値目標はないが、可能な限り高速に。上記Astro選定の主要因
- **セキュリティ**: 清水本人とパートナー以外がレシピを閲覧できないようにしたい → Cloudflare Accessで対応
- **コスト**: 無料枠内に絶対に収めたい → 全構成要素が無料枠内で完結することを確認済み
- **保守性・拡張性**: 個人開発のため、将来の機能追加・端末追加が容易であることを重視
- **PWA**: ホーム画面への追加は必要。オフラインキャッシュ（電波なしでの閲覧）は不要

## リポジトリ構成

```
kitchen-log/
├── CLAUDE.md                        # 概要＋@import（常に全体に読み込まれる）
├── .claude/
│   ├── settings.json                 # レシピ作成用の最小権限（コミットする）
│   ├── settings.local.json.example   # 開発用権限のテンプレート（コミットする）
│   ├── settings.local.json           # 開発用権限の実体（.gitignore対象、一度もpushしない）
│   └── commands/
│       └── new-recipe.md             # レシピ登録スラッシュコマンド
├── docs/
│   ├── superpowers/specs/            # 設計ドキュメント（本ファイルなど）
│   └── workflows/
│       ├── authoring-workflow.md     # 4つの入口とレシピ登録フロー
│       ├── nutrition-rules.md        # 栄養計算式・benefits/cautions記述ルール
│       ├── naming-conventions.md     # 食材名・タグの重複防止ルール
│       ├── data-boundary.md          # リポジトリ vs Supabaseの切り分けルール
│       └── step-writing-guidelines.md # 手順文の執筆ガイドライン
├── recipes/                          # レシピ本体（JSON、フラット構成、1レシピ1ファイル）
├── profile.md                        # 好みプロファイル（清水・パートナー・共通、1ファイル）
└── viewer/                           # Astro製PWAビューア（Step2以降で実装）
    ├── CLAUDE.md                      # 開発規約（コミット、viewer配下アクセス時のみ遅延ロード）
    ├── src/
    ├── astro.config.mjs
    └── package.json
```

### 設計判断の理由

- **`recipes/`はフラット構成**: カテゴリ別サブフォルダを作らない。`dish`と`tags`はフラットな配列で階層を作らない方針（後述）と一貫させるため。フォルダ階層を作ると複数軸での絞り込み（例:「唐揚げ」でも「揚げ物」でも探せる）がしにくくなる
- **`profile.md`は1ファイル**: 清水とパートナーの好みは、共通の食事を作る前提上、同時に参照する場面が大半であり、2ファイルに分けると「世帯共通の方針」の置き場所が曖昧になる。Markdownの見出しで人物ごとに分ける

## AI運用環境の設計

### 課題と要件

このリポジトリは2つの文脈で使われる。

1. **クラウド上のClaude Code**（claude.ai/code、モバイルブラウザ経由）: レシピについて相談し、確定したらリポジトリにコミットする「レシピ作成」用途
2. **ローカルPCのClaude Code**: `viewer/`のAstroアプリを開発する「開発」用途

要件は非対称である。「クラウドがレシピ作成の権限を超えて開発的な操作をできてしまう」ことは防ぎたいが、「ローカルがレシピ作成モードで動く」ことは問題ない。また開発端末は1台とは限らない。

### 解決策: gitの可視性を利用した構造的なガードレール

Claude Codeの`.claude/settings.json`と`.claude/settings.local.json`は次の仕様を持つ（claude-code-guideエージェントによる公式ドキュメント確認済み）。

- 優先順位: Local > Project > User
- `settings.local.json`はgitignore対象の個人設定であり、ローカルCLIのみに見える
- クラウド環境（claude.ai/code）もGitHubからのチェックアウト時に、ローカルCLIと同じ優先順位でコミット済み`.claude/settings.json`を読み込む（確認済み）
- gitignore対象で一度もpush/commitされていないファイルは、gitの基本的な仕組み上、どのチェックアウト先にも物理的に存在し得ない

これにより、以下の構造的な保証が成立する。

| ファイル | git管理 | 内容 |
|----------|---------|------|
| `.claude/settings.json` | コミットする | レシピ作成に必要な最小限の許可のみ（`recipes/`・`profile.md`・`docs/`へのWrite/Edit、git add/commit、URL入力用のWebFetch）。**クラウドが持てる権限の上限そのもの** |
| `.claude/settings.local.json` | .gitignore対象、一度もpush/commitしない | 開発用の追加許可（`npm run dev`・`npm test`、`viewer/`への広いEdit許可等） |
| `.claude/settings.local.json.example` | コミットする（テンプレート） | 新しい開発端末では、これをコピー＆リネームするだけでセットアップ完了。空ファイルではなく実際の権限内容を持つテンプレートなので、コピーだけで機能する |

開発端末が何台に増えても、`settings.local.json`が一度もリモートに存在しない限り、クラウド側が開発権限を得ることは構造的に不可能。これはCLAUDE.mdの指示文をClaudeが正しく読んで従うかどうか（保証されない）に依存せず、ツールの実行許可自体がファイルの有無で決まるハーネス側の仕組みに基づく。

### CLAUDE.md / viewer/CLAUDE.md の役割分担

- **ルート`CLAUDE.md`**: レシピ作成ワークフロー（`docs/workflows/*.md`への`@import`の束）。常にクラウド・ローカル両方に読み込まれる
- **`viewer/CLAUDE.md`**: Astroの開発規約（コンポーネントの書き方、開発サーバーの起動方法等）。コミットするが、サブディレクトリのCLAUDE.mdは起動時にはロードされず、**Claudeがそのディレクトリ内のファイルを実際に読みに行った時にのみ遅延ロードされる**（公式ドキュメントで確認済み）。レシピ作成のワークフローは`recipes/`・`profile.md`・`docs/workflows/`しか触らないため、`viewer/`配下には一切アクセスせず、`viewer/CLAUDE.md`は読み込まれない
- **`CLAUDE.local.md`**: 個人限定のメモ用（gitignore対象）。開発規約はここに書かない（開発規約は共有すべき知識であり、gitで管理して全端末で自動的に一致させるべきため）。本プロジェクトでは基本的に未使用の想定

`@path/to/file.md`のインポート構文は無条件の静的インクルードのみサポートし、条件付きインポートには対応していない（公式ドキュメント: "Imported files are expanded and loaded into context at launch"）。今回は「常に全部読み込ませたい」用途なので、この制約は問題にならない。

### `docs/workflows/` の各ドキュメント概要

- **authoring-workflow.md**: 4つの入口（①CookGo→PDF共有 ②レシピサイト/YouTube URL ③テキスト貼り付け ④ゼロベース相談）から、同じスキーマのJSONに収束させる流れ
- **nutrition-rules.md**: 文部科学省「日本食品標準成分表2020年版（八訂）」のエネルギー計算式を固定式として明記:
  `エネルギー(kcal) = たんぱく質(アミノ酸組成)×4.0 + 脂質(脂肪酸TG当量)×9.0 + 利用可能炭水化物(単糖当量)×3.75 + 食物繊維×2.0 + 糖アルコール×2.4 + 有機酸×3.0 + アルコール×7.0`
  食塩相当量の目標値（成人男性7.5g未満/日、女性6.5g未満/日、厚労省「日本人の食事摂取基準（2025年版）」）も明記。`benefits`/`cautions`は「計算した栄養素の値」と「公的基準値との比較」からのみ記述可能とし、俗説・都市伝説は禁止
- **naming-conventions.md**: 新しい食材名・タグを作る前に`recipes/`をGrepして既存表記を再利用するルール（専用辞書ファイルは作らない）。`dish`（同一料理の識別子）と`tags`（フラットな横断属性）の使い分け
- **data-boundary.md**: 「Claude Codeのみが参照・更新＝リポジトリ、アプリからも＝Supabase」の切り分けルール（v2機能はまだ実装しないが明文化しておく）
- **step-writing-guidelines.md**: 映像がない前提で、誰が読んでも迷わない手順文を書くためのガイドライン
  1. 状態変化を必ず言葉で描写する（「きつね色になるまで」等、動画なら一目でわかる変化を具体的な視覚・聴覚・嗅覚の目安表現に置き換える）
  2. 時間・火加減の目安を必ず併記する（「中火で3分ほど」等）
  3. 「いつも通り」等の省略表現を禁止。各手順は単独で読んでも実行できるように書く
  4. 専門用語には簡単な補足を添える（例:「面取り（角を削って煮崩れを防ぐ下ごしらえ）」）
  5. 1ステップ＝1アクションを基本にする（Step3の調理モードで1ステップずつ大きく表示する設計と一貫させるため）

### `.claude/commands/new-recipe.md`（カスタムスラッシュコマンド）

4つの入口のどれであっても、以下の同じ手順を踏ませることで、ルールの飛ばしを防ぐ。

1. 入口の種類（cookgo/url/text/zero）を確認し、元情報を取得
2. `profile.md`を読み、好みを反映
3. `recipes/`をGrepして食材名・タグを既存表記に寄せる
4. `ingredientSections`（セクション別・id付き変数）と`steps`（`{{id}}`参照）のJSONを組み立てる。手順文は`step-writing-guidelines.md`に従う
5. 栄養計算・benefits/cautions・バランス評価を実施
6. スキーマ検証（後述）を実行
7. ユーザーに確定前レビューを提示
8. 確定後、`recipes/<slug>.json`に保存しgit commit

## レシピJSONスキーマ

```jsonc
{
  "id": "example-recipe",              // ファイル名(slug)と一致、レシピ全体でユニーク
  "title": "レシピ名",
  "dish": "dish-identifier",           // 同一料理の複数レシピを束ねる識別子
  "tags": ["タグ1", "タグ2"],           // フラットな横断属性（階層なし）
  "servings": 2,                        // このレシピが書かれている基準人前

  "ingredientSections": [
    {
      "section": "合わせ調味料",         // フェーズ名は自由記述（固定リストなし）
      "items": [
        { "id": "sauce_sake", "name": "酒", "amount": 1, "unit": "大さじ" },
        { "id": "sauce_soy",  "name": "醤油", "amount": 1, "unit": "大さじ" }
      ]
    },
    {
      "section": "炒めるとき",
      "items": [
        { "id": "stirfry_sake", "name": "酒", "amount": 1, "unit": "小さじ" },
        { "id": "salt", "name": "塩", "amount": null, "unit": "少々" }
      ]
    }
  ],

  "steps": [
    "{{sauce_sake}}・{{sauce_soy}}を混ぜて合わせ調味料を作る。",
    "具材を炒め、{{stirfry_sake}}を加えて香りを出す。仕上げに{{salt}}で味を調える。"
  ],

  "nutrition": {                        // 1人前あたり、八訂の計算式でClaude Codeが算出
    "energyKcal": 420,
    "proteinG": 18.2,
    "fatG": 12.5,
    "carbohydrateG": 58.0,
    "saltG": 3.1
  },
  "benefits": [],                       // 公的基準値との比較から言えることのみ。無ければ空配列
  "cautions": ["食塩相当量がやや高め（目標値の4割強）"],
  "balance": "野菜量が控えめ。既存レシピの「ナムル」等の副菜と組み合わせると良い。",

  "source": { "type": "cookgo", "note": "PDF共有経由" },  // type: cookgo/url/text/zero
  "createdAt": "2026-07-07",
  "updatedAt": "2026-07-07"
}
```

### 設計判断の理由

- **`ingredientSections`（セクション分割）**: 同じ調味料・食材でも使われるフェーズが違えば別エントリ・別idにする（例: 合わせ調味料の「酒」と炒める時の「酒」）。手順文の`{{id}}`参照が一意に定まるようにするため
- **単位の固定列挙**: 表記ゆれと栄養計算のブレを防ぐため、`unit`は日本の家庭料理基準の固定値のみ許可する
  - 重量: `g`
  - 体積: `ml`, `大さじ`, `小さじ`, `カップ`
  - 個数: `個`, `本`, `枚`, `束`, `片`, `玉`
  - 定性的: `少々`, `適量`, `ひとつまみ`（`amount`は`null`許容。人前スケーリング時も変化させない）
- **`amount`は常に数値（`少々`等を除く）**: 人前スケーリング時の丸め処理（CookGoの「酒5/8大さじ」のような非実用値を避ける）はビューア側（Step2）の責務とする
- **`benefits`/`cautions`は空配列を許容**: 無理に埋めない
- **`id`のユニーク性**: セクションをまたいでレシピ全体でユニークである必要がある（Zodスキーマのカスタム検証で担保）

## `profile.md` の構成

```markdown
## 共通
（世帯として意識していること。例: 最近は減塩を意識したい）

## 清水
（個人の好み。例: 辛いものが好き）

## パートナー
（個人の好み。例: 苦手な食材）
```

Claude Codeがレシピ作成時に参照し、レシピ確定のたびに学習した内容を追記していく「蒸留された記憶」として運用する。

## スキーマ検証・エラーハンドリング

- Zodスキーマを`viewer/src/schemas/recipe.ts`に1箇所定義し、以下の2箇所で共有利用する
  - Astroの`content.config.ts`（Content Collectionsのビルド時検証）
  - `/new-recipe`コマンド実行中、確定前レビューの直前にClaude Codeが実行するスタンドアロンの検証スクリプト（`id`のセクション横断ユニーク性チェックを含む）
- コミット前に検証を通すことを`/new-recipe`の手順に明記し、壊れたJSONがリポジトリに入らないようにする
- GitHub ActionsでCI検証（push時に全レシピをスキーマチェック）を追加し、手動編集等で崩れた場合も検知する

**Step0に含む`viewer/`の範囲について**: 上記のZodスキーマ・`content.config.ts`を成立させるため、Step0では`npm create astro@latest`相当の最小限のAstroプロジェクト雛形（`package.json`・`astro.config.mjs`・`content.config.ts`・`viewer/src/schemas/recipe.ts`・`viewer/CLAUDE.md`）を作成する。ページ・コンポーネント・レイアウト等の画面実装は一切含まず、それらはStep2の範囲とする。

## スコープ外（本ドキュメントでは扱わない）

- Step1: 実際の4入口からのレシピ変換・保存の検証作業そのもの
- Step2: Astroビューアの画面設計・コンポーネント実装
- Step3: 調理モードの画面実装
- v2: お気に入り・週間予定表・買い物リストのSupabaseスキーマ設計
- Cloudflare Pages / Cloudflare Access の具体的なセットアップ手順
